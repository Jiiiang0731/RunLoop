## 二、算法优化（目标 ①②）

### 2.1 问题诊断（阶段 I 遗留）

阶段 I 对所有距离统一用「圆形 + 自适应控制点数」骨架。真实 API 探索暴露两个问题：

1. **转弯数 ≈ 控制点数**：每个 waypoint 附近路网通常强制一次转弯。15km 用 9 点圆环 → 转弯密度高达 2.0~2.2 次/km。
2. **单一骨架收敛脆弱**：某些 seed 下圆形骨架会陷入「距离断层」（R 缩放无法把道路距离拉进 ±500m），阶段 I 的 15km seed1 就因此失败（−674m）。

### 2.2 探索标定（真实 API，`backend/explore_phase_j.py`）

对 15km 做了多骨架 × 多 seed 的系统探索（结果存 `backend/out/explore_j_*.json`）：

**15km seed2（9 种骨架配置）：**

| 配置 | 点数 | 轴比 | 达标 | 评分 | 转弯 | 密度 | HTTP |
| --- | --- | --- | --- | --- | --- | --- | --- |
| base_n9（阶段 I） | 9 | 1.0 | ✓ | 41.0 | 31 | 2.03 | 69 |
| cir_n6_lj | 6 | 1.0 | ✓ | 43.9 | 27 | 1.79 | 63 |
| **ell15_n6** | 6 | 1.5 | ✓ | **51.0** | **24** | **1.65** | **27** |
| ell19_n6 | 6 | 1.9 | ✓ | 39.3 | 33 | 2.12 | 43 |
| ell22_n5 | 5 | 2.2 | ✓ | 33.9 | 33 | 2.24 | 41 |
| ell15_n7 / cir_n7_lj / ell13_n6 | — | — | ✗ 距离断层 | — | — | — | — |

**15km 跨 seed（验证收敛互补性）：**

| seed | base_n9 | ell15_n6 |
| --- | --- | --- |
| 1 | ✗ +1407m | ✓ **−126m，评分 69.3，17 转弯，密度 1.14** |
| 2 | ✓ +237m，41.0 | ✓ −496m，51.0 |
| 3 | ✓ +450m，53.6 | ✗ −1105m |

**结论**：没有单一骨架对所有 seed 都收敛，但 **ell15_n6（6 点、轴比 1.5）与 base_n9 恰好互补**——seed1 只有椭圆收敛且质量极高，seed3 只有圆形收敛。这正是「多变体扫描 + 择优」的依据。

**20km 探索**：ell15_n6 同样胜出（seed1 密度 1.25/评分 56.3，seed2 密度 1.57/评分 50.3），而 ell15_n7（7 点）两个 seed 都距离断层。据此把少点变体的点数系数从 0.68 校正到 **0.62**（15km base9→6、20km base10→6、10km base6→5）。

### 2.3 最终算法（`variants.py` / `calibrator.py` / `generator.py`）

**骨架变体序列**（`plan_variants`，按 seed/距离确定性展开）：

1. **lean_ell**：少点椭圆（点数 = round(base×0.62)，轴比 1.5，低抖动 0.10，seed 推导角度）——主减转弯变体，最先尝试；
2. **base**：圆形多点（自适应点数，抖动 0.15，迭代预算 8）——收敛兜底；
3. **lean_cir**：少点低抖动椭圆（轴比 1.3，另一角度）——仅当前两者都可能不达标时的第三救援。
- 当减点无意义时（5km base 已是 5 点）只返回 base 单变体，避免重复消耗。

**质量感知选择**（`calibrate`）：
- 每个变体做 R 缩放迭代逼近目标距离；每个成功闭环立即用 `nav_metrics` + `score_route` 算真实评分（零额外 API）。
- 全局保留「达标候选中评分最高」者（`_is_better`：达标优先 → 评分 → 误差）。
- **提前终止**（`_should_stop_early`）：某闭环达标且（评分 ≥ 50 或 密度 ≤ 1.5 且无掉头且急弯 ≤ 1）即停，省下后续变体调用。
- **变体级止损**：已试 ≥ 2 变体且已有达标路线 → 接受，不再试第 3 个（第 3 变体只作收敛救援），避免长距离成本膨胀。

**多候选择优**（`rank_candidates`）：达标候选按评分降序，最高分标 `recommended`，失败候选置后。服务端候选按此顺序返回，老 APK 向后兼容。

### 2.4 API 稳健性修复

- **指数退避重试**：`AmapWalkingPlanner` 重试改为 0.25s→0.5s→1s 指数退避；识别高德限流 infocode（10003/10004/10019~10023/10044）用加倍退避。修复了当日累计调用后 QPS 限流导致的成片失败。
- **每种子调用预算** `per_seed_calls=160`，硬性护栏防止失控。

## 三、路线显示美化（目标 ③）

### 3.1 插件补丁（`packages/amap_flutter_map`）

高德 Flutter 插件原生层早已解析 `gradient`/`colorList`/`zIndex`，但 Dart 层未序列化，且 `PolylineController.setGradient` 有 bug（误调 `setGeodesic`）。本地补丁：

- `polyline.dart`：新增 `gradient`(bool)、`colorList`(List<Color>?)、`zIndex`(double?) 字段并在 `toMap` 序列化；`copyWith` 补 `gradientParam`/`colorListParam`/`zIndexParam`；更新 `==`。
- 原生 4 文件：`PolylineOptionsSink`(+`setZIndex`)、`PolylineUtil`(读 `"zIndex"`)、`PolylineOptionsBuilder`(`zIndex()`)、`PolylineController`（修复 `setGradient` 用 `useGradient`+`setOptions`，`setZIndex` 用 `polyline.setZIndex`）。
- **构建期修复**：`PolylineOptions` 的 z-index 是 builder 式 `zIndex(float)` 而非 `setZIndex(float)`（后者只在运行时 `Polyline` 上存在）——首轮构建暴露、已修正。

### 3.2 统一视觉方案（`lib/utils/route_style.dart`）

- **选中路线**：白描边（9.5dp，zIndex 10）+ 渐变主线（5.5dp，zIndex 20）+ 圆角端点/连接（Google Maps 式包边）。三条候选渐变：蓝→青 / 橙→琥珀 / 紫→粉。
- **未选中路线**：主色降透明度（alpha 60）3dp 细线，zIndex 5，不喧宾夺主。
- **去/返程重叠**：保留阶段 G 的 ±10m 视觉偏移，每段独立描边+渐变。
- **起点标记**：绿色圆形徽章 + 白环 + 白旗（`createStartIcon`）；方向箭头改为主色箭形 + 白描边（任何底图都清晰）。
- **性能**：静态覆盖物缓存 + 生长线/跑者用固定 id 逐帧 `copyWith` 原地更新，杜绝阶段 H 的「每帧删旧加新」卡顿。

### 3.3 候选页交互增强（`route_candidates_screen.dart`）

- 候选卡片：主色圆点 + 「推荐」徽章（`recommended`）+ 转弯数/密度/评分。
- 「换一批」：每轮用一组新种子（7,8,9 → 10,11,12 …），与现有路线**合并后按「达标优先+评分降序」重排**，最多保留 3 条。
- App 各处改为 `points: 0`（后端自适应控制点数），修复阶段 I 遗留的「前端硬编码 points:10 绕过自适应」问题。

## 七、遇到的困难

1. **高德 QPS/配额限流**：当日累计 ~2000+ 次真实调用后触发限流，导致成片 `build_loop` 失败、10km 出现 +4085m 的异常闭环、15/20km 直接 FAILED。跨日配额重置 + 指数退避重试后恢复。**教训**：真实 API 探索/基准必须控制节奏、识别限流 infocode 并退避。
2. **骨架收敛的 seed 依赖性**：同一配置在不同 seed 下可能收敛（−126m）也可能距离断层（−1105m）。无法预知哪个骨架对哪个 seed 收敛——只能用「多变体扫描 + 择优 + 兜底」覆盖，代价是失败变体会消耗调用预算。
3. **容差硬悬崖**：20km 探索中 lean_ell 曾以 +543m（仅超容差 43m、评分 49.4、32 转弯）被拒，回退到 base 的 +52m（评分 33.4、45 转弯）——一条明显更差的路线因 43m 之差被选中。靠把 lean 变体 max_iters 从 5 提到 6（多一次 R 缩放收敛进容差）解决，但暴露了固定 ±500m 绝对容差对长距离偏紧。
4. **少点变体的迭代预算**：lean 变体点数少、单次构建便宜，但 R 缩放收敛慢（20km 需 ~6 次）。预算太小会卡在容差外白白回退，太大又浪费调用——需按距离标定（已定为 6）。
5. **原生 API 命名差异**：`PolylineOptions.zIndex(float)`（builder 式）vs `Polyline.setZIndex(float)`（运行时）——首轮构建才暴露，文档未明确区分。

## 八、模棱两可 / 待用户决策的问题

1. **容差是否应改为相对值？** 当前 ±500m 绝对容差对 20km 是 2.5%、对 5km 是 10%。长距离是否放宽到 `max(500, 3%×目标)` 更能收敛到少转弯路线？（会改变「达标」语义与前端显示，未擅自更改。）
2. **质量 vs 调用成本的取舍点**：10km 为把转弯从 35 降到 23，调用从 21 升到 35、耗时从 4.8s 升到 8.8s。是否值得？提前终止阈值（评分 50）是否应按距离分档？
3. **骑行 API 不可用**：本 Key 的骑行路径规划返回 `10002 SERVICE_NOT_AVAILABLE`，只能用步行 API。步行路线可能含人行道/过街天桥等不适合跑步的段——是否需要用户实地确认，或申请骑行权限？
4. **重复率 32~48%**：环线去/返程天然有重复（评分维度之一）。少点椭圆已把重复率压到 ~0.32，但无法消除。是否可接受，或需要「8 字形/花瓣形」进一步降重复（会更复杂、更费调用）？
5. **后端绑定局域网 IP**：`ROUTE_API_BASE_URL` 默认 `http://192.168.1.100:8000`，换网络即失效。是否需要推进公网 HTTPS 部署（`docs/public_deployment_plan.md`）？
6. **偏航阈值 120m / 投影窗口 250m**：基于城市 GPS 误差经验值，未经真机长距离跑测标定，可能需要按实际 GPS 表现微调。
