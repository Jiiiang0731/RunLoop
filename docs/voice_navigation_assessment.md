# 语音导航技术评估（阶段 E · 预研）

> 目标：为「自定义闭环路线 + 分段导航步骤 + 本地 GPS」设计可行的语音播报方案。
> 本阶段只做技术评估与最小原型设计，不实现完整导航系统。

| 能力 | 现状 |
| --- | --- |

## 2. 方案 A：本地 TTS + 自行判断转弯（推荐先做）

### 2.1 原理

1. 用已保存的分段步骤（本地 SQLite 中的 `steps`，含 `cumulative_m` 与每步折线）。
2. 用 GPS 当前位置，计算「距离下一个转弯点」的沿路线距离（用累计距离差，而不是直线距离）。
3. 在阈值（如 100m、30m）触发系统 TTS 播报下一步指令。
4. 偏航检测：计算当前点到路线折线的最近距离，超过阈值（如 50m）提示「已偏离路线」。

### 2.2 技术选型

- TTS：`flutter_tts`（系统 TTS，支持中文、耳机音频路由、语速调节）。
- 后台定位：`flutter_foreground_task`（前台服务 + 通知，保持定位与播报）。
- 沿路线投影：对每段折线做「点投影到线段」计算，得到当前累计里程（已有 `haversine` 可复用）。

### 2.3 需要处理的问题

| 问题 | 处理方式 |
| --- | --- |
| 定位漂移 | 用 GPS 精度过滤 + 沿路线投影平滑；偏航判定需连续 N 次超阈值 |
| 转弯指令时机 | 用「沿路线累计距离差」而非直线距离；提前 100m/30m 两档播报 |
| 重复播报 | 每个 step 记录 `lastAnnouncedAt`，同一档位只播一次 |
| 耳机播报 | 交给系统 TTS（走媒体/通话音频路由），不强制指定扬声器 |
| 偏航检测 | 到折线距离 > 50m 持续 10s → 提示「已偏离路线」，可选重新投影 |
| 后台/锁屏 | 前台服务（`FOREGROUND_SERVICE_LOCATION` 已声明） |
| 进度恢复 | 保存「已播报 step 索引 + 上次定位时间」，重开时恢复 |
| 电量 | 定位频率 2s、仅跑步中开启前台服务 |

### 2.4 可行性结论

**可行，推荐优先实现。** 数据基础（steps + 折线 + 累计距离）已具备，主要工作量在：
1. 沿路线投影与偏航判定；
2. TTS 触发状态机；
3. 前台服务与通知；
4. 进度持久化。

## 3. 方案 B：高德 Android 导航 SDK

### 3.1 能力

- 专业转向播报、路口放大图、偏航重算、语音包。

### 3.2 与现有架构的冲突

1. **自定义路线不匹配**：导航 SDK 以「起终点 → 自行算路」为主，环跑是自研环线算法生成的折线，需要 `AMapNaviPath` 自定义注入，接入成本高。
2. **缺少 Flutter 绑定**：官方无 Flutter 插件，需要自写 PlatformChannel，风险与工作量都大。
3. **Key/配额**：导航 SDK 与 Web 服务、地图 SDK 的 Key 体系不同，需额外申请与配额评估。
4. **体积**：导航 SDK 会显著增大 APK。

### 3.3 结论

**暂不推荐。** 除非后续要做「专业级路口放大图/实时重算」，否则方案 A 足够覆盖「按自定义路线播报转弯」。

## 4. 实现顺序（建议）

1. 数据层：确认 `steps` 含 `cumulative_m` 与折线（已完成）。
2. TTS 最小原型：手动触发「前方 100 米右转」播报。
3. 自动触发：GPS 投影 → 距离下一转弯 → 阈值播报 → 去重。
4. 偏航检测 + 提示。
5. 前台服务 + 锁屏播报。
6. 进度恢复 + 历史回放。

## 5. 风险

- 城市峡谷/高架下 GPS 漂移，偏航误报；
- 系统 TTS 中文语音质量因机型而异；
- 后台定位在部分国产 ROM 上被限制（需引导用户加白名单）；
- 电量与发热。

## 6. 本阶段结论

**方案 A 可行且与现有数据模型契合；方案 B 成本高、与自定义环线不匹配，暂缓。**
建议下一阶段先做「TTS 最小原型 + 沿路线投影」，再逐步补偏航与后台能力。
