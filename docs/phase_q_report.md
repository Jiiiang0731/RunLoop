## 2. 性能基线与瓶颈定位（先测量，后改代码）

对 1/2.5/5/15 km 用与 App 相同参数（同起点 `114.027494,30.535040`、`seeds=[1,2,3]`、`max_candidates=1`、`fix_detours=true`）做只读剖析：

| 目标 | 总耗时 | HTTP 墙钟 | API 占比 | 本地几何/评分 | 缓存命中 | 备注 |
|---|---:|---:|---:|---:|---:|---|
| 1 km | 3.95 s | 3.24 s | 82.1% | <0.01 s | 0 | 非 API 0.71 s ≈ 14 段 × 0.05 s 固定 sleep |
| 2.5 km | 30.49 s | 26.15 s | 85.8% | <0.01 s | 4/93 | **25 次 10021 QPS 重试** / 114 次 HTTP |
| 5 km | 19.35 s | 16.61 s | 85.9% | 0.01 s | 2/60 | 固定 sleep ≈ 2.7 s |
| 15 km | 35.41 s | 30.67 s | 86.6% | 0.02 s | 4/105 | 固定 sleep ≈ 4.7 s |

结论（有证据，不是猜测）：

1. **真正瓶颈是高德 HTTP 延迟 + QPS 限流**，不是 Python 几何/评分（CPU 总计 <1%）。
2. 2.5 km 的 114 次 HTTP 里 **25 次是 `10021`（调用频率超限）重试**；当前串行速率已经超过 Key 的 QPS，盲目并发只会增加限流与重试。
3. 2.5 km 的 110 次调用中，66 次花在 6 个变体，44 次花在“激进修复 → 修短超差 → 3 次重校 → 最后部分修复”。真实数据：只用前 2 个变体 + 一次距离感知部分修复，即可得到完全相同的 2565.9 m，调用降到约 28。

## 3. 本次实现的优化

### 3.1 进程级成功路径缓存（`backend/route_generator/planner.py`）

- 键：起终点各保留 **6 位小数（≈0.11 m）**，**方向敏感**——绝不假设 A→B 与 B→A 相同；
- 只缓存 `error is None` 的成功结果；失败绝不入缓存；
- TTL 600 s、最多 2048 条，LRU 淘汰；可用 `RUNLOOP_WALK_CACHE_TTL_S` / `RUNLOOP_WALK_CACHE_SIZE` 覆盖；
- **in-flight 合并**：同键请求已在飞时，其它线程等待并复用结果；
- `/api/health` 暴露 `cache` 统计（hits/misses/evictions/waits/size），不含坐标/密钥。

### 3.2 全局限速与固定 sleep

- 新增进程级令牌桶，默认 **3 QPS**（`RUNLOOP_AMAP_QPS`），每次 HTTP 尝试（含重试）先取令牌；
- 服务端 `sleep_s` 默认 0.05 → **0.0**，去掉每段固定 sleep；由令牌桶统一控制节奏；
- 证据：2.5 km 25 次 10021 重试 → 优化后多轮测量只有偶发 1 次。

### 3.3 候选搜索早停与“先修复”

`backend/route_generator/calibrator.py`：

1. **硬容差内 + 质量合格 + 已试 2 次构建**：停止继续换骨架，转入局部修复（不是“进入 ±500 m 就收工”）；质量门槛包括闭环<50 m、无不适合跑步路段、重复率≤75%、转弯密度/数量、长距离分数≥45 且密度≤2.5。
2. **单变体还有 R 迭代空间时，多探一次**再停：5 km 若在 iter2=5348 m 直接修复会得到 4768 m（质量下降）；多跑 iter3=5320 m 后再修复保持 4901 m。
3. **距离感知部分修复优先**：旧顺序“激进修复→修短→3 次重校→最后部分修复”在 2.5 km 花 44 次调用；把最后一步提前，4 次调用即可得到同样的 2566 m。
4. **已进入内部目标带且干净**（含 `find_spur_intervals` 检查）时跳过所有绕行修复：5/15 km 实测修复不改变最终距离，纯浪费调用。
5. **远误差变体跳过**：某变体连续 2 次仍偏离 >max(3×tol,15%) 时停止该变体的 R 迭代（15 km lean_ell 31→19→18→10→18→9.6 km 的振荡），交给 base 兜底。
6. 1.5 km 内仍不做激进绕行切割，守住 1 km 精度；spur_fix 的 partial accept 增加 `tight` 距离守卫。

### 3.4 有限并发调研结论

- 用两个相距约 1.9 km 的起点、各 1 km 目标，分别做“串行两次”和“同时两次”：
  - 串行总耗时 **28.53 s**；并发总耗时 **28.36 s**（-0.6%，无实质增益）；
  - 并发时单个请求反而更慢（A 9.1→16.5 s，B 19.2→28.2 s），因为共享同一个全局令牌桶；
  - 基线已出现 10021，说明 Key 的 QPS 是全局上限。
- 结论：**不启用请求内并发**；服务端并发闸仍为 2，但 HTTP 启动由 3 QPS 令牌桶统一调度。继续增加并发只会增加限流重试与配额浪费。

## 5. 前向偏航重规划

### 5.1 请求契约（新增字段，全部可选；旧客户端不传 = 旧行为）

客户端上传：

```json
{
  "origin": {"lng": 114.0226, "lat": 30.5378},
  "polyline": [[lng,lat], "..."],
  "along_m": 1980,
  "target_m": 5000,
  "completed_m": 2000,
  "tol_m": 500,
  "heading": 205.6,
  "heading_source": "recent_points",
  "heading_confidence": 0.9,
  "heading_age_ms": 120,
  "speed_mps": 3.0,
  "accuracy_m": 5,
  "offset_m": 10,
  "recent_points": [[lng,lat,accuracy,speed,timestamp_ms], "..."],
  "route_end": [lng,lat],
  "original_total_m": 4938,
  "forward_only": true,
  "request_id": "req-7",
  "sent_at_ms": 1793870000000,
  "max_api_calls": 6,
  "min_forward_gain_m": 10,
  "max_backtrack_m": 25,
  "max_initial_angle_deg": 90
}
```

### 5.2 服务端算法（`backend/reroute.py`）

1. **真实当前位置**：把 `origin` 投影到原路线（±500 m 窗口），得到 `actual_along_m`，不再直接信任客户端旧 `along_m`。
2. **方向仲裁**：
   - 最近 30 s、精度≤50 m 的 GPS 点 → 连续位移方向（首选，`recent_points`）；
   - 单点原生 bearing 且速度≥1 m/s（低置信度兜底）；
   - 最近可靠方向（短暂停止/GPS 差，`frozen`，≤30 s）；
   - **路线切线/指南针不作为主来源**；全部不可信 → `HEADING_UNRELIABLE`。
3. **未来接回点**：从 `actual_along + max(80m, 8%剩余)` 到原路线终点采样；结构上排除已跑过/身后点；切线方向与 heading 夹角>90° 的候选**不评估**。
4. **连接段真实校验**（每个高德真实步行连接段）：
   - 首段方位与 heading 夹角 `initial_angle_deg`；
   - 前 80 m 前进增益 `forward_gain_m`；
   - 前 80 m 最大回退 `backtrack_m`；
   - 任一不满足（>90°、<10 m、>25 m）→ `forward_ok=false`，不参与选择。
5. **剩余预算**：`estimated_total = completed + connector + (original_total − rejoin_along)`；剩余目标<80 m → `REMAINING_DISTANCE_INFEASIBLE`。
6. **选择**：仅在 `forward_ok` 候选中选；优先 `within_tolerance`，再按“距离误差 + 0.5×连接段 + 12×转弯 + 方向/回退惩罚”最小。
7. **前向替代路线**：没有可接回点或全部反向时，从当前位置沿 heading 前进 300/600 m 等短探针，再规划到原终点；仍要求首段向前；每次尝试 2 个真实请求，预算硬上限。
8. **合并与校验**：连接段 + 接回点 + 原路线尾段；首点距 origin≤50 m、尾点距原终点≤50 m，否则 `ROUTE_ASSEMBLY_ERROR`。
9. **不静默掉头**：全部候选反向/回退 → `NO_FORWARD_REJOIN`；无法构造替代路线 → `NO_FORWARD_ROUTE`；请求过期 → `STALE_REQUEST`；上游限流 → `AMAP_ERROR`。

### 5.3 错误码与用户提示

| 错误码 | 含义 | 客户端行为 |
|---|---|---|
| `HEADING_UNRELIABLE` | 无法可靠判断当前前进方向 | 语音/横幅提示“请继续沿道路跑几秒后重试”；不生成路线；运动继续 |
| `NO_FORWARD_REJOIN` | 前方接回点都需要掉头/回退 | 明确提示；不应用旧路线；可手动重试 |
| `NO_FORWARD_ROUTE` | 无法生成合理的前向替代路线 | 明确提示；不强制掉头 |
| `REMAINING_DISTANCE_INFEASIBLE` | 剩余目标距离过短/无法满足 | 明确提示；不为了闭环强拉长路线 |
| `ROUTE_ASSEMBLY_ERROR` | 新旧路线连接失败 | 提示重试；不接入坏路线 |
| `STALE_REQUEST` | 请求/进度过期 | 提示重试；丢弃过期结果 |
| `AMAP_ERROR` | 高德限流/失败 | 提示稍后重试；运动继续 |

保留阶段 M：请求 ID、在飞锁、冷却 30 s、自动重试≤2、过期结果按 ID 丢弃、绝不结束运动。

### 5.4 真实高德 API 验证

**正向成功（5 km 路线，沿路 10 m 偏移）**：

- `success=true`, `strategy=forward_rejoin`
- `actual_along_m=1999.9`（客户端旧 along=1980）
- 首段夹角 **0.4°**、前进增益 **96.9 m**、回退 **0.0 m**
- 接回点 `along=3136.0`（前方 1136.1 m），`forward_ok=true`
- 连接段 889.0 m；剩余 2691.0 m；预计总 4691.0 m（比 5000 m 目标少 309 m，`within_tolerance=false`，客户端如实提示“比原目标少 0.3 km”）
- 合并剩余路线首点距 origin 约 1.5 m，尾点为原路线终点
- API 2 次 / 0.47 s

**反向拒绝 1（平行道路 55 m 偏移）**：

- `NO_FORWARD_REJOIN`；所有候选首段夹角 96.3°、回退 28.1 m、前进增益 0 m → 全部拒绝，未生成掉头路线。

**反向拒绝 2（错过 126.6° 路口后继续直行 60 m）**：

- `NO_FORWARD_REJOIN`；所有候选首段夹角 133.1°、回退 60.0 m、前进增益 5.1 m → 全部拒绝。
- 该道路网络上若接回原路线必须返回路口；系统选择如实报告，而不是静默生成掉头路线。符合任务书“宁可如实报告无法生成”。

**离线 A–H 测试**：14 项，覆盖正向接回、无身后点、反向拒绝、多候选方向优先、方向不可靠、最近点恢复方向、剩余过短、连续偏航、过期请求、前向替代路线、旧路径不变。全部通过。

### 5.5 客户端方向与安全防线

- 新增 `lib/utils/heading_estimate.dart`：最近 30 s、精度≤50 m 的连续 GPS 点计算稳定方向；停止/信号差回退最近可靠方向（frozen，≤30 s）；单点 bearing 仅低置信度兜底；绝不使用指南针/路线切线。
- 请求携带方向来源/置信度/年龄、速度、精度、偏移、最近 9 点、原终点、原总里程、request_id、sent_at；`forward_only=true`。
- 客户端第二道防线：`forwardAcceptable` 检查 `forward_ok`、首段夹角≤90°、回退≤25 m；不满足则抛 `NO_FORWARD_REJOIN`，绝不应用。
- 连接段序列化修复：最后一步不再无条件标记 `end`（旧实现会在接回点提前播“已到达路线终点”）；前向替代路线才保留 `end`。客户端 rebase 时若连接段已含 end，不再追加旧 end。
- 失败时语音/横幅显示具体错误；结构性失败（NO_FORWARD_*）不做无意义自动重试；网络/限流/方向不可靠仍按冷却自动重试≤2。
