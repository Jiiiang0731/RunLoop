## Q1. 为什么 1km/5km 短距离差，而 50km 能出漂亮大环？[已确认]

### 真实数据（E3/E1）

| 目标 | seed | 实际距离 | 误差 | 重复率 | 说明 |
|---|---|---|---|---|---|
| 1000m | 1 | 1249m | +24.9% | **0.572** | 5 点骨架，1 次构建即被采纳 |
| 1000m | 3 | 1298m | +29.8% | — | |
| 1000m | 4 | 1324m | +32.4% | — | |
| 1000m | 5 | 1285m | +28.5% | — | 35 次调用（R 振荡后） |
| 1000m | 6 | **586m** | **−41.4%** | — | **用户看到的 0.6km 已复现**；64 次调用仍不收敛 |
| 2500m | 1 | **1524m** | **−39.0%** | 0.594 | R 在两个值间来回振荡 |
| 50000m | 1 | 达标 | — | — | E1：213 次调用 / 55s 完成 |

### 根因（四条，互相叠加）

1. **几何骨架尺度与短距离不匹配**：`R_init = target/(2π·1.7)`（calibrator.py:124）。
   1km → R≈93.6m，5 个控制点相距 ~110m，全落在同一街区内；
   50km → R≈4681m，骨架跨越主干路，距离-半径关系近似单调，所以"大环"好看。
2. **容差被当成终止条件**：`calibrator.py:155 _should_stop_early`、`:158 abs(e)<=tol_m → break`、
   `:166` 变体级止损。tol_m=500 对 1km 是 **50% 相对容差**——第一条进入 ±500m 的路线立即收工。
3. **评分把 400m 误差当 95 分**：`scorer.py:24-31 distance_error_score`
   ±300m 内满分、2300m 才 0；且 `DEFAULT_WEIGHTS["distance_fit"]=0.10`（10%）——
   586m 与 970m 的总分只差约 4.6 分，几乎等价。
4. **R 用定点迭代，而距离对 R 高度不连续**：2.5km 实测 R=234.1→4652m、R=169.1→1524m
   （28% 半径变化 → 3 倍距离跳变），迭代在两点间无限振荡
   （`diag_routes.json` 中 base#0 与 base#2、base#1 与 base#3 完全重复）。

补充：`adaptive_n_points` 对 ≤7km 固定 5 点；`variants.lean_n_points(5)==5` ⇒
`plan_variants` 只返回单一 `base` 变体（variants.py:60-61），短距离没有第二次机会。

**1km 出现 0.4/0.6km 仍被接受的产品逻辑**：
`server.py:237 within = abs(err) <= tol_m` → 586m 判为"合格"；
预览页只在 |err|>500 时才弹二次确认（route_candidates_screen.dart:696）。

## Q2. 为什么总是小路/角落/短支路/碎片，而不是大路？[已确认]

1. **用的是步行 v3 API**（`planner.py:124 /v3/direction/walking`），
   而实测（E3 原始响应）：步行 v3、骑行 v4、驾车 v5 在这片区域返回**完全相同的几何**
   （128m/311m/523m 三段），且 `steps[].road` 为空数组 `[]`。
   ⇒ **三种模式都没有道路等级/宽度/名称信息**。
2. **算法没有任何"大路"维度**：scorer 五维 = 转弯/直行/重复/急弯/距离，
   nav_metrics 也只看几何（nav_metrics.py）。
   控制点相距 ~110m 时，步行规划只能给出"最短可走路径"——在街区内部就是贴墙、穿巷、绕楼，
   算法无法判别，只能全盘接受。
3. **碎片化实测**：2.5km 候选 1524m / 12 步 / 6 次转弯 → 转弯密度 **3.96 次/km**
   （理想 ≤0.3–0.5），步长中位 122m。
4. **重复/重叠实测**：1km 候选重复率 **0.572**（>50% 里程原路往返）——
   这正是"去返程完全重叠"的来源（不只是绘制问题，路线本身就在折返）。

**诚实结论**：现有三个高德 Web API 无法提供道路等级/宽度/照明数据，
"优先大路"只能靠：(a) 几何/结构代理指标，(b) 引入真实道路属性数据源（见第五节决策 2）。

## Q3. 为什么偏航重规划 4–5 次全部失败？[已确认：两个独立原因]

### 原因 1（直接原因）：部署进程陈旧，端点 404

E1 真实日志：

```
2026-11-05 16:08:52 INFO dev=f2ccb0e7 POST /api/route/reroute -> 404 0ms
... 共 9 次（16:08:52 – 16:13:17），全部 404
```

E2：`/api/health` 返回 `version: "0.5"`，uptime 80515s，
PID 35476 启动于 **2026-11-04 18:08** —— 早于 reroute 端点提交（293c4f4）。
⇒ 手机每次都收到 HTTP 404，客户端显示"重新规划失败"。**与算法无关。**

已处理：重启为当前 v0.6（`/api/health` → `version 0.6`）。

### 原因 2（重启后立即暴露）：候选选择与里程口径错误

E4 真实响应（1km 路线，along=300m，偏离 60m）：

```
success=True  api_calls=5  elapsed_s=0.7
rejoin.along_m=1022.6  skipped_m=722.6  connector_m=90.0
remaining_m=304.2  estimated_total_m=604.2  within_tolerance=True   ← 604m 对 1000m 目标判"达标"
候选：along=380 connector=106 extra=+26 score=+26
      along=1023 connector=90  extra=-632 score=-632  ← 被选中（最负=最优）
```

- 评分 `score = extra_m + 12×turns`（reroute.py:235），
  `extra_m = connector_m − skipped_m`（:233）⇒ **跳过越多原路线得分越好**；
  系统因此选择"跳过最多剩余路线"的候选（本次直接接到终点，丢掉 723m）。
- `within_tolerance` 用的是固定 ±500m（reroute.py:237），
  604m vs 1000m = −40% 仍判达标，App 不显示任何提示。

### 原因 3（未在真机复现，但代码必然）：锁屏时不会触发重规划

所有触发逻辑在 `build()` 内（见 Q4），锁屏后不执行 ⇒ 后台偏航不会发起任何请求。

## Q4. 为什么锁屏后没有语音？（不是权限）[已确认，源码级]

1. `run_screen.dart` 唯一调用 `_onMatched(...)` 的位置在
   `ListenableBuilder(builder: ...)` 内（构建期，约 :1027）。
   `_onMatched` 内部依次执行：`_updateNavState`（偏航状态机）、
   `_announcer.onPosition/onKmSplit`（**全部语音播报**）、`_checkGoal`（目标播报）、
   `_nextTurnHint`（转弯提示）。
2. Flutter 框架（E6）：
   `scheduler/binding.dart:424-426` `case AppLifecycleState.paused: _setFramesEnabledState(false);`
   `:947` `if (_hasScheduledFrame || !framesEnabled) return;` → 暂停态不调度帧、不 build。
3. 因此锁屏后：GPS 继续记录（定位流在事件循环，不依赖帧）、计时器继续跑，
   但**没有任何一次播报被触发**——与用户描述"GPS 在记录，但没有语音"完全一致。
   这与权限、引擎、音频焦点都无关：代码从未调用 speak。

VoiceLog 应呈现的签名（用于真机确认修复）：`lifecycle paused` 之后到 `resumed` 之前
没有任何 `speak` 条目；恢复前台后集中出现一批。
**[需真机]** 用 VoiceLog 证明修复后 paused 期间仍有 speak→start→done。

## 2. 最小化修改方案（按影响排序，不动无关模块）

**P0-A 部署与版本握手**（RC-1，已完成重启）
客户端启动时读 `/api/health` 版本；服务端版本低于 App 要求时在生成页明确提示
「服务端版本过旧，缺少重规划接口」，避免再次把 404 显示成"重新规划失败"。

**P0-B 锁屏可用性**（RC-3，前端，1 个文件 + 测试）
把 `_onMatched` 从 `build()` 移到 `_onRecorderTick()`：
`_recorder.addListener(_onRecorderTick)` + `Timer.periodic(1s)` 兜底
（paused 时 timer 仍在事件循环执行）；`build` 只做渲染。
加 VoiceLog 心跳（每 30s 记录 `fgs/started/points/km`），真机可直接证明锁屏期间逻辑在跑。

**P0-C 距离拟合**（RC-4/5/6，后端 3 个文件 + 测试）
1. `distance_error_score` 改陡峭非饱和（相对误差 10% → 0 分），权重从 10% 提到 ≥30%；
2. 早停条件从 `|err|≤500m` 改为 `|err| ≤ max(30m, 5%·target)`（1km→50m，5km→250m）；
3. 短距离（≤3km）专用：矩形/椭圆骨架 × 半径网格（R×{0.7,0.85,1.0,1.15,1.3}）× 2 形状，
   取 `min |err|` 且通过质量门限者，**不再做 R 定点迭代**；
4. 短距离控制点数从 5 提到 8（街区尺度需要更多拐点才能贴合路网）；
5. 仍以 ±500m 为硬上限（超限则不给"推荐"，明确提示"该区域无法生成接近目标的路线"）。

**P0-D 重规划正确性**（RC-2，后端 1 个文件 + 测试）
候选评分改为：`|completed + connector + (total − rejoin_along) − target|` 最小优先，
`skipped_m` 作为惩罚项；`within_tolerance` 用相对容差；失败保留真实 error_code
（NO_REJOIN / AMAP_ERROR / BAD_REQUEST / RATE_LIMITED）并写入诊断日志。

**P1 视觉重做**（RC-8/9，前端 3–4 个文件 + 多缩放自动化检查）
去返程双轨（overlap passes → 两条屏幕偏移折线，仅视觉）、粗线
（casing 9dp / core 7dp，类高德）、导航页方向箭头（zoom 自适应间距 200–400m）、
真实转弯位置左/右/掉头标记、GPS 轨迹独立配色。

**P2 道路质量门限**（RC-7）
用真实 steps 的结构指标做硬门限：中位步长 <60m 或短步段占比 >40% 或
转弯密度 >3/km 的候选直接拒绝；短/长距离参数分开。

**P3 数据缺口**（RC-10）
坡度/车流/道路等级：AMap 免费 Web API 不提供。若需要，只能引入真实数据源
（OSM/Overpass 的 highway/lit/surface，需 WGS84→GCJ02 转换与版权署名）——待用户决策。

### 为什么现有算法找不到这条环线（已确认）

1. 环线包围盒 ≈ **730m × 960m**，中心 ≈ (114.1674, 30.4380)，
   而用户起跑点在西北角 (114.1645, 30.4420) —— **路线中心与起点偏移 ~450m**；
2. 算法骨架是「以起点为圆心的同心圆/椭圆」：2500m 目标 R=234m，
   8 个控制点全在起点 234m 内，**永远到不了东南侧远角**；
3. R 增大到能覆盖远端时，控制点落进无路/院内区域，规划被迫大绕行
   （实测 R=234 → 7682m，R=187 → 1662m），无法收敛；
4. 锚点参与后，真实道路本身可以形成 2987m 的干净闭环 ——
   证明**路网里有这条路线，问题在搜索范式（同心骨架）而不在数据**。

### 结论与策略调整

- 「先画圆/椭圆 → 连控制点」的范式在**偏心、非对称**的自然环线面前必然失败；
- 改为「**道路网络优先**」：从起点沿真实道路生长闭环
  （辐条探测 + 环边连接 + 半径/点数自适应），并用
  **驾车可通行比率 + walk_type（台阶/地下通道/天桥）** 作为真实质量门限；
- 用户提供的 10 个锚点作为**有序参考锚点**（不作为精确转弯点），
  用于验证与回归，并可作为「自定义经典路线」功能输入。

### OSM 数据可行性（用户已选择引入 OSM）

实测结论：**当前网络不可得** ——
`overpass-api.de` 502/504、`overpass.kumi.systems` 超时、
`api.openstreetmap.org` 连接超时、`overpass.osm.ch` 返回空数据集
（`timestamp_osm_base: 118246`，为无真实数据的测试实例）。
⇒ OSM 道路等级方案在当前部署环境无法落地；
替代方案：①为服务器提供可访问 OSM 的代理；②沿用上面的 AMap 真实代理指标
